## 1. 真实执行路径与范围

现有实现是：

```text
手动输入（只选本卦、动爻、起卦时间；问题不参与计算）
 → 原固定 worker / 原 Frame 签名与来源校验
 → ValidatedJudgementInput
 → 固定 Day7A 判断引擎重新读取原资格
 → build_request → 有封印的 QualityRequest
 → CandidateProvider.generate：QuestionIntent + 四角色 ApplicationDraft
 → validate_draft
 → IndependentReviewer.review：独立会话，重新读取完整依据与草稿
 → validate_verdict
 → 确定性渲染；任何失败返回原基础卦义
```

`backend/question_quality_v1/pipeline.py` 目前只有离线 Provider 协议和 Mock。`backend/app/deepseek.py` 的真实 Provider 只支持固定连通性诊断，不支持上述问事草稿/审核；没有问事 API 路由。

意图提取已包含在候选草稿内，**不需要额外一次意图调用**。未来每例至多两次请求，六例最多 12 次；用户提出的 18 次只是外部最高边界，剩余 6 次不作为重试、修补或备用模型调用预算。本轮不实现真实传输，不调用旧生产问事服务绕开新契约，不调用连通性接口“预热”。

真实测试只能在获批后新增的隔离验收执行器进行；不接普通网页、不签发生产批准、不写生产历史或语义缓存。实施该执行器和通过零费用运输替身验收后，才能开始获批的付费请求。

## 4. 获批后的顺序

1. 校验授权范围、预算、固定 Provider/model/HTTPS、禁重定向、禁重试、非流式输出、只读基线与所有六例证据。
2. 六例串行，B01→B06；禁止并发批量、替换测试问题或增加测试案例。
3. 每例重新签发受控请求，核对本轮基准计算/Frame/来源/资格指纹。任何偏差先停止，不发送。
4. 一次候选请求包含意图和四角色应用。严格解析、不人工修 JSON、不自动重试；本地 gate 失败则无需支付审核请求。
5. gate 通过才发送一次独立审核：重新给原问题、冻结计算、完整原子、来源、条件与草稿，不给生成器会话/推理/自评分。
6. 六项全部 true、score≥3、所有绑定一致才能通过契约；之后逐条独立原文审查，不以回执分数代替语义核对。
7. 只在专属测试报告保存经过白名单处理的合成样例结果；普通网页和旧历史不接受本次解释。
8. 任一严重安全问题立即停止所有剩余请求，保留失败原因及标准回退；不为提高批准率再生成、修补或换模型。

真实审核只是独立会话，仍可能与生成模型相关误判。原始来源审查是另一层，不能把两个同厂商请求称为两套传统证据。

## 5. 独立来源抽查

对实际得到候选的全部四角色逐条核对，计划最多 **6例×4角色＝24组**，不只看已选中的 core_claim。记录：Frame ID、原子范围、source evidence ID、原文摘录/位置、conditions/cautions、Day7A条件/分支、应用句、支持或扩大原因。

特别核对 B01 取舍、B02 宾客范围、B03 过失、B04 小/大分支、B05 亢极与无互争议、B06 不知限度。需要原页时只读已有本地扫描资料，不搜索新来源或改写已批准 Frame。来源无法读出或范围不确定，判来源核验未通过，退回基础解读。

本轮尚无真实候选，故这24组的**应用语义一致性未验证**；已经实际检查六例输入与原资格、来源绑定可读，不等于24组应用质量通过。
