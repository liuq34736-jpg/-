# 下一阶段问事解释质量建议（未实施）

依据是只读的 [Day 3 失败分析](day3_question_quality_analysis.md)，以及原系统最终验收/问题清单。没有改旧资料、Frame、签名、历史、审核阈值或问事正文。

Day 4 只接入通过验收的确定性计算和标准解释。旧问事质量结论仍为 FAIL；不能以成功连通 API 或改造 UI 代替质量修复。

## 建议实施顺序

1. 在独立网页应用适配层复现原 F-01～F-04 和同义对抗样例，先不调用付费 API。
2. QuestionIntent 的每条事实绑定用户原话跨度，区分已提供事实、未来询问、过去背景、愿望和未提供信息。行业常识不能冒充用户事实。
3. 每条应用类比绑定现有 Frame ID 与只读原典条件；明确区分传统基础含义和现实应用，不把市场/支出/对方动机推定为现状。
4. 逐分句检查条件范围、否定式结果保证、金额/日期断言、时令被解释成现实状态等边界。无法证明条件继承时回退，原审核门槛不降低。
5. 独立核验同时检查用户事实和来源条件；不能单凭同模型六项 true 或 score≥3 当可靠性证明。使用未参与开发的保留集做原典语义抽查。
6. 成功和失败缓存都绑定问题、输入卦象、时间、政策版本、证据指纹；新网页缓存独立保存，失败短期缓存避免重复收费。历史存当时正文和证据，回看只读快照，不重算/重释。
7. 在批准应用层缩短表达、去重、减少古语，但不得借改写增加来源没有的含义。先离线验收，再经单独授权做小量真实调用。

每步应提供事实越界数、来源语义一致率、实际批准率/回退率、可读性、缓存零调用和逐字回放证据。修复未通过前维持当前标准卦义，不开放自由正文流式展示。
